## 0. 调研结论（已完成的代码考察）

**"dsh 2.0" = 0.2.x 版本线**，没有真正的 2.0.0：0.2.0-rc.1 发布于 2026-09-28，最新为
`dsh-v0.2.1-rc.2`（2026-10-17，npm dist-tag `next`）。本地 `D:\code\deepseek-harness`
已 checkout 到该 tag，以下结论全部来自对该版本的源码阅读（关键接口均已一手核实）。

| 调查项 | 结论 |
| --- | --- |
| 插件定位 | **不变**。0.2.x 完全没有原生 A2A / Agent Card / `.well-known` 能力（全仓库零命中）。ACP 是本地 stdio、无认证的可信控制器；`packages/api` 网关是 DSH 私有 Typert 协议（只服务自家 Web/桌面客户端）；subagent 只能指向本机进程。入站 A2A 插件的差异化价值完整保留。 |
| API 耦合面 | 逐项核对了插件用到的 10 组 API：**8 组完全不变**（agents.create/get、followup/whenIdle/cancel、agent/inbox/claimed、session/event、createUserMessage、credentials、webServer、cordis 插件约定）。2 组破坏性变更 + 1 组打包机制变化，见下文。 |
| 插件分发 | npm 仍是主渠道；`dsh plugin --profile <name> add <pkg>` 不变（但 `--profile` 必须放在 pnpm 参数之前）。0.2.x 新增去中心化 Plugin Markets（可选 Discover 页）与 `engines.dsh` 兼容判定。 |
| 常驻形态 | 官方姿势是自定义 profile 常驻（`--profile <name> --from-default-profile web`），headless profile 是一次性的、不开端口，不适合常驻在线。 |

## Part A：dsh-a2a-server 升级（0.2.0 → 0.3.0，目标 DSH 0.2.1-rc.2）

### A1. 必改代码（两处）

**A1-1 `src/projection.ts`：ProjectionDefinition 接口重构（最大破坏点）**

0.2.1 把 projection 单元从「单 schema + 顶层 view」改为「state / wire 双层」。已对照官方迁移范例
`packages/session/session-turn-outline`（一手核实）：

| 现状（0.1 写法） | 0.2.1 要求 |
| --- | --- |
| `schema: A2A_TASK_VIEW_SCHEMA`（顶层，校验 wire） | `stateSchema`（校验 **state**）；wire 校验移入 `wire.viewSchema` |
| `view(state)`（顶层函数） | `wire: { viewSchema, view }`（client 可见键必须提供 `wire`） |
| declaration merge 只声明 `SessionProjectionMap.a2aTask` | **双表**：`SessionProjectionStateMap.a2aTask: A2ATaskState_` + `SessionProjectionMap.a2aTask: A2ATaskProjection` |

- `init()` 零参函数仍可赋值（兼容）；`apply` 不变；`stateVersion` 保持 `2`（state 形状与折叠语义都没变，旧缓存可延续）。
- 我们的 state 与 view 结构相同，`stateSchema` 与 `viewSchema` 可复用同一个 zod 对象。
- 不改的后果不只是编译错：`register` 运行时读 `definition.stateSchema`，旧 `schema` 字段会被静默无视。

**A1-2 `src/index.ts`：subagents 清理方法改名**

`drainContinuableDescendants` → `drainDescendants`（签名不变，2026-09-17 起）。
只改 `ContinuableDrain` 结构接口和一处调用点。

### A2. 顺手清理（小，建议一起做）

- `src/index.ts` 写入 `approval/policy` 时的 `source: 'a2a'`：官方联合收紧为 `'delegation'`。
  untyped append 不会报错、fold 忽略 source，但建议去掉该字段（或改 `'delegation'`）保持干净。
- `cordis.patch.yml` 里残留 `protocolVersion: '0.3.0'`：config schema 早已没有这个键，是死配置，删除。

## Part B：开放互访实现计划

定位（2026-10-21 澄清）：**让别的访客（人或别的 agent）能直接跟用户的 AI 聊**。
dsh 在线 agent 常驻（跑 dsh-a2a），访客的 agent 通过 A2A 发现它、跟它对话、派任务；
用户的 AI 也能反向来找别的 agent（出站）。宿主日常 agent 与 dsh 在线 agent 共享同一个
repo workspace 和同一个 skill 目录。

**仓库形态（2026-10-21 第三轮拍板：两仓库拆分）**：

- **本仓库（dsh-a2a）**：只做 dsh-a2a-server 插件，含 B1 开场注入（插件功能）。
- **新仓库（待建）**：宿主 agent 开放化的用户侧交付——a2a-skill（B2）、a2a-handoff
  （B3）、组网与部署文档（B4）、接待 prompt 模板。前置依赖：dsh + dsh-a2a-server。
- 协议库复用不需要 monorepo：插件包已通过 `dsh-a2a-server/protocol` 子路径导出
  零依赖协议库，新仓库直接依赖 npm 包即可。

### B0. 宿主背景简报（`.hop/handoff.md`）：内容、写读双方、与数据的关系

**简报承载的是工作记忆，不是数据。** 它回答"dsh 在线 agent 接待访客时需要知道主人的
哪些背景"，四要素：最近在做什么（意图与进度）/ 改了哪些文件（动过哪里）/ 关键决定
（为什么这么改）/ 未完事项（还差什么、有什么坑）。大小约束在 1–2KB（几百 token）量级。

```markdown
---
updated: 2026-10-21T22:00:00+08:00
author: claude-code   # 写入方：宿主日常 agent（覆写式）或 dsh（追加式）
---
## 最近在做什么
...
## 改了哪些文件
...
## 关键决定
...
## 未完事项
...
```

**谁来写、谁来读：撰写者永远是产生上下文的那个 agent；hooks 与配置只负责到点触发，
不负责理解内容：**

| 动作 | 宿主日常 agent（claude code / zcode 等） | dsh 在线 agent（接待访客） |
| --- | --- | --- |
| 写 | Stop/SessionEnd hook 触发，由在场模型自己写出（文件清单/TODO 可脚本机械提取，意图/决定由模型蒸馏） | prompt/skill 指示：在合适节点把记录 append 到同一文件 |
| 读 | SessionStart hook 读入注入 | B1 开场注入：访客 context 建立时作为首条消息 |

**工作目录里的大量数据不走简报，因为目录本来就是共享的。** 存储分三层：

| 层 | 内容 | 共享方式 |
| --- | --- | --- |
| repo / 工作目录（长期记忆） | 代码、文档、数据文件 | 无需传递：宿主 agent 们的 workspace 指向同一 repo（`isolation.peerWorkspaces`），dsh 在线 agent 用 fs 工具直接读 |
| `.hop/handoff.md`（工作记忆） | 意图、进度、决定、待办 | 唯一需要显式传递的东西——因为这些只存在于模型上下文里，session 结束即丢失 |
| 各家会话历史（jsonl 等，私有记录） | 完整对话流 | 不传递、不互读 |

代码改动同理：写进文件的部分 git 与文件系统里都在，在线 agent 需要知道的不是 diff
本身，而是"为什么改、改到什么程度、还差什么"——即简报四要素。

**指令 / 记忆 / skills 的处理边界**（2026-10-21 第二轮拍板）：

| 类别 | 例子 | 处理（拍板） |
| --- | --- | --- |
| memory 与 AGENTS.md | ~/.claude、~/.zcode 的用户指令与 auto-memory、repo 里的 AGENTS.md/CLAUDE.md | **不交接**，不做任何机制处理——它们定义"agent 是谁"，不是"接待访客需要什么背景" |
| skills | deploy-talktome、lark-cli、a2a-skill 等用户技能；repo 内的项目级 skill | **共享 skill 目录，两级**：用户级 `~/.agents/skills` + 工作目录级（repo 内 `.agents/skills`、`.claude/skills`、`.zcode/skills` 等项目 skill 目录）。dsh 侧两级都挂载，与 claude code / zcode 读同一份，不做翻译。实施时验证 dsh skill 体系挂载外部目录的配置方式与 SKILL.md 格式兼容性 |
| 通用用户偏好 | 文案纪律等对任何 agent 都适用的规矩 | 若需要，写进 dsh 在线 agent 的部署 prompt（B4），不走交接机制 |

dsh 在线 agent 自己的"上岗配置"（你是谁、repo 在哪、什么不许做）来自部署时写好的
prompt（B4），不来自任何交接。背景简报负责"主人的状态"，部署 prompt 负责"身份与规矩"，
两层分开。

### B1. 入站增强：开场背景注入（改 dsh-a2a-server，**已实现**）

- 配置 `preamble.files`（相对 peer workspace 的路径列表，默认 `[".hop/handoff.md"]`；
  文件不存在则跳过——"没有可交接的"是常态而非错误）
- Activation 建立时读入；实现采用**合并进该 context 首条访客消息**而非单独成

  记入任务边的 `input` 仍是访客原话（不含简报）

  简报是对话内容而非规矩；进会话日志可追溯
- **追加不做机制**：在线 agent 由 prompt/skill 指示，在合适节点把记录 append 到

### B1b. 本地监控读接口（改 dsh-a2a-server，**已实现**，2026-10-21 新增）

监控台（B5）与一切本地工具的数据源：

- `a2a/task` 边新增 `input`（访客原话）；projection `stateVersion` 2→3，折叠时
  终态边保留此前的 input——"谁说了什么、agent 答了什么"全部可从投影读出
- 只读路由 `{basePath}/admin/contexts[/<id>]`：GET、仅本机回环连接 + 独立
  `admin.tokenEnv` token 双闸；未配置 token 则整个监控面不挂载

### B2. 出站：`a2a-skill`（skill 形态，不用 MCP —— 2026-10-21 拍板；**新仓库**）

不用 MCP server：任何支持 skills 的 agent（claude code / zcode / dsh 自己）都能用，
且与"共享 skill 目录"的拍板天然融合——出站能力本身就是共享目录里的一个 skill。

- **交付物 = 一个自包含 skill 目录**（复制或链接进 `~/.agents/skills/a2a/`）：
  - `SKILL.md`：教 agent 何时去找别的 agent（触发条件）、怎么写自包含请求、
    怎么转述回信、通讯录怎么看
  - `bin/a2a.mjs`（Node CLI，复用 `dsh-a2a-server/protocol` 子导出的零依赖库做
    A2A v1.0 客户端）：
    `a2a contacts` / `a2a card <name>` / `a2a send <name> <text> [--wait]` /
    `a2a task <name> <id>`；输出简洁文本，供 agent 直接引用
  - 通讯录 `~/.a2a/contacts.yaml`：`name / url / token_env / note`；token 只从
    环境变量读，永不进模型上下文
- 与入站对称：对端是任何标准 A2A server（别人的 dsh-a2a 或其他实现）；本 skill
  只解决"我们的 agent 作为 A2A 客户端发起"
- dsh 在线 agent 从同一共享目录读到这个 skill：访客派来的任务若需要再找第三方
  agent，它自己就会用

### B3. 上下文迁移统一入口：`a2a-handoff`（转换器路线；**新仓库**）

**为什么是转换器，不是改 dsh 内核的适配器**（2026-10-21 拍板）：

1. DSH 的 session log 是私有 append-only 事件格式，且 pre-release 期间高频重构
   （本次 0.1→0.2 升级就亲历了 projection 接口重构）。适配器等于把别家格式的语义
   钉死在 dsh 内核里，DSH 每次升级都得重做一遍，维护成本无上限。
2. 各家 agent 的会话格式之间不存在事件级无损映射（工具调用 schema、turn 结构、
   思考块语义都不同）。硬转换会造出"看似完整实则失真"的历史，比一份显式的语义
   快照更危险——下游会信任它。
3. 改内核违背 DSH "everything is a plugin" 的架构，也失去官方升级路径。
4. "复制一份会漂移"的担忧对交接单不成立：交接单本来就是**快照语义**，双方约定
   以文件系统为交接媒介；源 agent 继续演进它的历史，交接单记录"到此刻为止的状态"。
5. 转换器对每家 agent 是独立的 reader 模块，逐个增援；适配器每支持一家都要动内核。

**设计**：

- 统一入口 CLI：`a2a-handoff --from <agent> [--session <id>] [-o .hop/handoff.md]`
- 两层结构：
  - **reader 层**（每家 agent 一个模块，注册表选择）：读该 agent 的会话存储，
    输出规范化的中间格式 `Transcript`（消息序列 + 工具调用摘要 + 会话元数据）
  - **蒸馏层**（共用一份）：`Transcript → handoff.md`（frontmatter：最近在做什么 /
    改了哪些文件 / 关键决定 / 未完事项）
- 用户按需选择支持哪些 agent：`--from claude-code | zcode | codex | kimi-code | workbuddy`
- reader 实施顺序：claude code（`~/.claude/projects/*.jsonl`）→ zcode → codex /
  kimi code / workbuddy（各家存储格式实施时逐个调研）
- 消费侧就是 B1 的开场注入；各家 agent 的触发方式（Claude Code 的 Stop/SessionEnd
  hook、其他 agent 的等价机制）都只是调这个 CLI

### B4. 《配置与启动指南》文档（**新仓库**，M2）

面向终端用户的一篇文档（中英双语，中文先行），从零到对外可达。结构：

1. **它是什么 / 安全模型**：访客能做什么、不能做什么（per-peer 隔离、审批自动
   拒绝、限流、白名单），四层防御一览（网络 → 身份 → 应用 → 系统层）。
2. **前置条件**：Node 22+、dsh、（可选）Docker、DeepSeek API key。
3. **五步上手**（每步含命令与逐字段解释）：
   ① 建 profile + 装插件（`--from-default-profile web`；`--profile` 在最前）；
   ② 配置：card 名片 / peers 与 token 发放（`openssl rand -hex 32` →
     `~/.dsh/.credentials.yaml`）/ workspace 指向 / provider + model；
   ③ 网络三档：局域网（`--host`）/ tailscale（推荐）/ cloudflared（公网域名 + TLS）；
   ④ 交给访客：URL + Bearer token 的发放话术；访客侧三种形态
     （人用 curl / 对方也是 dsh / claude code·zcode 装 a2a-skill 写通讯录）；
   ⑤ 验证：curl agent-card + SendMessage 通一句话 + probe 脚本。
4. **进阶**：Docker 隔离部署（volume 定向挂载清单：repo `:ro`、两级 skill 目录、
   `.hop/`）；接待 prompt 模板；开场注入 `preamble.files`。
5. **运维**：token 轮换（改 credentials 即时生效）、停机、日志、故障排查
   （端口占用 / engines 兼容判定拒绝 / key 未配置）。

**对外实例的隔离（2026-10-21 定稿：默认 dsh 内置沙箱，Docker 降为可选强隔离档）**：

- **dsh 内置沙箱（默认）**：dsh 自带进程沙箱（`sandbox-policy`：`read-only` /
  `workspace-write`），bash / 文件 / 终端调用全部受限、越权直接拒绝，跨平台
  （Windows 用 ACL），零额外依赖。控制台生成的 overlay patch 里直接带
  `sandbox-policy` 配置行（按 id 覆盖 base 组合的默认行）。
- **Docker 容器（可选强隔离）**：整套环境进容器，只暴露一个端口；key 与 token 经 env
  注入。适合完全不受信的开放场景；共享资产用 volume 定向挂载（repo 默认 `:ro`、
  skill 目录、`.hop/`）。
- 分层防御合计：网络层（tailscale/反代 + TLS）→ 身份层（per-peer token）→
  应用层（trustedPeers 白名单 / 限流 / 审批自动拒绝 / per-peer workspace）→
  系统层（内置沙箱或容器）。
- 检测屏缺项提供"复制安装指令（发给你的 Agent）"：一段自包含的代装指令，
  装完回屏点「重新检测」（2026-10-21 用户反馈落地）。
- Day-0：访客先以 curl 模板与运行中的 dsh-a2a 通第一句话（模板已在 README），
  再用装了 a2a-skill 的 agent（claude code / zcode）从反方向发起互访

### B5. `a2a-host` 配置控制台（UI；**新仓库**，M3，2026-10-21 新增）

**形态**：本地控制台 = CLI（`a2a-host`）+ 内嵌向导式 Web UI。`a2a-host ui` 按需
启动，配置完即关，**不常驻**；常驻的只有 dsh 本身。只绑 `127.0.0.1`——它是管
token 的主人控制台，绝不暴露到网络（不做鉴权，靠"只听本地"保证安全）。

**页面流（首次 = 向导；再次打开 = 控制台/监控台）**：

| 屏 | 内容 |
| --- | --- |
| 0 检测 | dsh 版本 / Docker 有无 / API key 状态；缺什么就地给安装指引 |
| 1 名片 | agent 名字、描述、skills 标签（实时预览 Agent Card 效果） |
| 2 模型 | provider / model / credential 状态 |
| 3 访客 | 逐个添加（名字 → 一键生成 32 字节 hex token）；每人生成"发给访客"复制块（URL + token + 一句话说明）；白名单开关 |
| 4 工作区与隔离 | 选 repo 目录、per-peer/shared、Docker 开关（开→展示挂载清单，repo/skills 默认 `:ro`，可逐项放开） |
| 5 网络 | 三选一（局域网 / tailscale / cloudflared），每档显示待执行命令与 publicUrl 预览 |
| 6 预览与启动 | 将写入的全部内容 diff 式预览（overlay patch / credentials / compose）→ 一键写入并启动 → 内置验证（card + SendMessage）结果就地展示 |

控制台模式（非首次，即**监控台**）：在线状态、访客管理（吊销 = 改 credentials，
即时生效）、**谁来访过/都聊了什么**（渲染 B1b 的 admin 快照：按访客分组的
会话时间线，每条任务展示访客原话与 agent 回答，可按访客/时间/状态过滤）、
停/重启。不做 dsh 官方 Web UI 的 client 插件（2026-10-21 拍板）。

**落盘机制（核心原则：不碰用户已有配置）**：

- 控制台自建 `--profile a2a`（web 模板）并安装插件；生成的配置写**独立 overlay**
  `~/.a2a/host.patch.yml`，启动时带 `--patch ~/.a2a/host.patch.yml`——利用 dsh 的
  layer 机制（后层按 id 整行覆盖），不污染用户手写的 profile patch
- token 写 `~/.dsh/.credentials.yaml`（编辑前自动备份）
- Docker 档生成 Dockerfile + docker-compose.yml 到 `~/.a2a/`

**技术**：CLI 用 Node/TS（复用 `dsh-a2a-server/protocol` 子导出）；UI 用
Vite + React（与 dsh web 生态一致）；CLI 起本地 HTTP（127.0.0.1，随机端口）供
UI 调 REST；监控数据直接调插件的 B1b admin 接口；一切写入操作先展示 diff 再执行。
