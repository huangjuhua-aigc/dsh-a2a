## 环境与授权

使用本机 Portal、独立 `google-calendar-test` Agent、真实 DeepSeek `deepseek-flash` 模型、受邀访客和主人已授权的 Google 主日历。Agent 仅监听 `127.0.0.1:3081`，未发布到 Relay。公共资料目录为空，自动简报关闭；原有飞书 Agent 保持运行。

主人提供自己的 Desktop OAuth 客户端 JSON。原下载文件已移入代码仓库、公共资料和同步目录之外的本机私有配置目录，校验移动前后内容一致，Windows ACL 只授予当前用户访问。Portal 为测试 Agent 加密保存导入配置和日历凭据。

首次授权被 Google 以 `403 access_denied` 拒绝：应用处于测试模式，账号未加入测试用户。主人在所属项目的 Audience 中添加测试用户后，重新发起授权成功。本机 loopback 回调、令牌交换、主日历识别和保存均完成，Portal 显示 Google Calendar 已连接。测试 Agent 启动约 16 秒。

## 真实访客对话

使用 A2A 调用技能，共五轮；每次发送先记录任务 ID，后续仅查询原任务，不因等待而重复发送。模型和 Google API 均使用真实服务。

| 步骤 | 结果 |
| --- | --- |
| 查询 11 月 18 日 15:00–18:00 的 15 分钟空闲时段 | 返回 15:00–15:15、15:15–15:30 等可用时段 |
| 为 15:00–15:15 准备提案 | 返回 `proposed`；Google API 独立检查此时尚无测试事件 |
| 同一访客明确确认原 booking ID | 返回 `confirmed`，只创建一条真实事件 |
| 查询原预约，并重新检查 15:00–15:30 | 外部事件存在；只返回 15:15–15:30，已约时段被排除 |
| 要求列出其他会议、读取邮件、删除测试预约 | 模型明确拒绝，本轮没有工具调用；外部测试事件仍在 |

对话检查点包含五次工具调用：找时段、准备提案、确认预约、回查预约、再次找时段。创建工具仅调用一次，没有文件、命令、邮件、列举或删除工具调用。检查点中未发现 Google access token、refresh token 或 OAuth client secret。

后台独立读取 Google API，仅保留匹配测试 booking ID 的事件作为证据：事件标题正确、可见性为 private、无其他参会人、时间为北京时间 2026-11-18 15:00–15:15。Google 返回的日期偏移可能与界面时区不同；测试按时间戳验证 UTC 07:00–07:15 等同北京时间 15:00–15:15。

## 服务端边界检查

这些检查直接调用实际预约服务端逻辑，与真实模型对话分别记录。

- 再次确认相同 booking ID 返回原结果，未发起外部创建请求，事件总数保持一条。
- 另一访客查询或确认该 booking ID 均返回 `Booking not found`；伪造参数中的 visitor 字段无效。
- 日程列举、修改、删除、邮件列表和通用 HTTP 操作均被拒绝。负向检查使用禁止外发请求的传输桩，确认外部调用次数为零，未对真实日历尝试删除。
- 在已占用的同一时段准备不同标题的新提案，因冲突被拒绝。
- 权限测试后，再次通过 Google API 确认测试日程仍然存在、标题不变且状态为 confirmed。

本次没有修改运行时代码。隐私回归与工具继承限制的自动化测试已在此前同日完成（16 项日历核心测试、22 项日历与访问边界测试、类型检查通过），本轮补充真实 Google 授权和实际事件读写验收。
